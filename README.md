# Instamart Customer Intelligence & Support Copilot

## Overview

One repository, four connected Parts, all on synthetic data (generated by the unmodified `generate_data.py`) and an offline mock model (the unmodified `mock_llm.py`). No network, API key or paid service is used. All money is in INR.

| Part | What it does | Main files |
|---|---|---|
| A | Audit and clean the raw exports, store them in SQLite, answer business questions in SQL and pandas | `src/part_a_clean.py`, `src/validate.py`, `src/part_a_sql.py`, `src/part_a_pandas.py`, `sql/queries.sql` |
| B | RFM segments (K-means) and a lapse-prediction model | `src/part_b_segments.py`, `src/part_b_lapse.py` |
| C | Support-ticket triage: guardrails, PII redaction, retries, validation, budget, routing | `src/part_c_triage.py` |
| D | Policy RAG assistant and a tool-using refund agent with safety limits and crash-resume | `src/rag.py`, `src/agent.py` |

Data flow: raw CSVs → Part A clean CSVs and `data/instamart.db` → Part B (`outputs/customer_segments.csv`) → Part C routing; Part A's database feeds Part D's `get_order` tool, and the agent reuses the Part D retrieval.

## Reproduce

Run from the repository root (Python 3.11+). Every script is deterministic (fixed seeds) and safe to re-run.

1. `python -m venv .venv`
2. `source .venv/bin/activate`
3. `pip install -r requirements.txt`
4. `python generate_data.py` (last line: `generated: customers=1200 products=40 orders_raw=13084 tickets=164`)
5. `python src/part_a_clean.py`
6. `python src/validate.py` (prints `ALL CHECKPOINTS PASSED`)
7. `python src/part_a_sql.py`
8. `python src/part_a_pandas.py`
9. `python src/part_b_segments.py`
10. `python src/part_b_lapse.py`
11. `python src/part_c_triage.py`
12. `python src/rag.py`
13. `python src/agent.py`

Order matters: Part B needs the clean files from step 5, Part C needs `outputs/customer_segments.csv` from step 9, and the agent needs `data/instamart.db` from step 5.

### Cleaning rules and what each changed

Customers
- City: strip spaces and title-case → exactly 6 cities (476 values changed). Result: Pune 227, Delhi 210, Bengaluru 197, Chennai 191, Hyderabad 191, Mumbai 184.
- Gender: `male/Male/MALE/M/m` → `male`, `female/Female/FEMALE/F/f` → `female`, blank → `unknown` (30). Result: female 610, male 560, unknown 30.
- Age: 6 values outside 10–100 set to missing; all 67 missing ages (61 blank + 6) filled with the median age of the customer's city using `groupby("city").transform("median")`. Result: 0 missing, ages 18–60.
- `signup_date` converted to datetime.

Orders (in this order)
1. `order_ts` converted to datetime (all 13,084 values).
2. Exact duplicate rows removed: 119.
3. For each `order_id`, only the record with the latest `order_ts` kept: 656 earlier "pending" records removed.
4. `order_amount` converted to numeric; unparseable entries rebuilt as `round(price_inr × quantity × (1 − discount_pct/100), 2)`: 112 values (120 raw unparseable entries, 8 of which sat in rows dropped by rules 2–3).

Then every missing `delivery_minutes` of a completed order (774 values: blanks plus the negatives) filled with the median of that order's product category among completed orders (`groupby(...).transform("median")`). Cancelled orders keep a missing delivery time (1,199), because a cancelled order was never delivered and imputing would invent data.

Result: 12,309 rows (one per `order_id`); 11,110 completed and 1,199 cancelled; no pending rows; 0 missing `order_amount`; 0 missing `delivery_minutes` among completed orders; completed revenue INR 2,998,668.80.

The elbow is at K=4: inertia falls by 525 from K=3 to K=4 but by only 126 from K=4 to K=5, and the silhouette peaks at K=4 (0.526). **Chosen K = 4**, which also gives four segments a campaign team can actually run. Inertia always falls as K grows (K=8 is lower than K=2) because more centroids always sit closer to the points, until each customer is its own cluster at inertia 0, so inertia alone would always pick the largest K; the choice needs the elbow, the silhouette and interpretability together.

### Lapse problem
Cutoff 2025-09-01. Cohort = 1,156 customers with at least one completed order before the cutoff; `lapsed` = 1 when there is no completed order from 2025-09-01 to 2025-09-30: 443 lapsed (38.32%). Split `train_test_split(test_size=0.2, stratify=y, random_state=42)`: 924 train, 232 test (89 lapsed in test). Features (orders before the cutoff only): recency, frequency, monetary, average discount, cancellation rate, average delivery minutes, favourite category, city, age, gender, tenure days. **No order dated on or after 2025-09-01 entered any feature, and the segment labels from Part B were not used as features.**

Baseline "always not lapsed": test accuracy 61.6%, lapsed-class F1 0.000.

### Preprocessing without leakage
A `ColumnTransformer` inside a scikit-learn `Pipeline`: `StandardScaler` on the 8 numeric columns and `OneHotEncoder(drop="first")` (k−1 columns) on city, gender and favourite category. **The encoder, scaler and resampler were fitted on training rows only; no test row was seen by any of them.** Feature columns contain 0 missing values (asserted in code). Learned scaler mean of frequency (train only) = 8.1147 versus the full-cohort mean 8.0285; they differ because the scaler's mean is computed from the 924 training rows only, which are a different sample from all 1,156 customers.

### Tuning and test evaluation (lapsed = positive class)

| Model | Best params | Best CV F1 |
|---|---|---|
| LogisticRegression (C ∈ {0.01, 0.1, 1, 10, 100}, cv=5) | C = 100 | 0.651 |
| RandomForest (max_depth ∈ {3, 5, 8} × min_samples_leaf ∈ {5, 10, 20}, cv=5, 45 fits) | max_depth 8, min_samples_leaf 10 | 0.681 |

| Test set | Confusion [[TN, FP], [FN, TP]] | Precision | Recall | F1 |
|---|---|---|---|---|
| Baseline | [[143, 0], [89, 0]] | 0 | 0 | 0.000 |
| Logistic regression | [[111, 32], [31, 58]] | 0.644 | 0.652 | 0.648 |
| Random forest | [[113, 30], [31, 58]] | 0.659 | 0.652 | **0.655** |

**Selected model: random forest** (test F1 0.655, above the 0.55 requirement). Missing a lapsing customer costs the lifetime value of a lost buyer, while wrongly targeting a loyal customer costs only one coupon, so recall matters at least as much as precision. The two models have identical recall (0.652), and the forest has slightly higher precision and CV F1, so it wastes fewer coupons for the same number of lapsers caught. It was chosen after tuning on cross-validation, and the test set was used only for this final comparison.

### Class-balance experiment
Training lapsed rows were randomly duplicated (with replacement, `random_state=42`, 216 duplicates added) until both classes had 570 rows; the best logistic regression was refitted on that set and evaluated on the unchanged test set.

| Logistic regression | Precision | Recall | F1 |
|---|---|---|---|
| Un-balanced | 0.644 | 0.652 | 0.648 |
| Over-sampled | 0.589 | 0.854 | 0.697 |

Recall moved most (+0.20, from 58 to 76 of 89 lapsers caught) while precision did not rise (it fell by 0.055). For the retention team this means they reach many more of the customers who really leave, at the price of about 21 more wrongly contacted loyal customers (53 false positives versus 32); that is worthwhile when a coupon is cheap compared with a lost customer.

### Interpretation, persistence, retention list
Top-5 random-forest importances: `frequency` 0.280 (few orders is the strongest warning sign), `monetary` 0.271 (low total spend goes with leaving), `recency` 0.115 (a long gap since the last order), `avg_delivery` 0.061 (slow deliveries are mildly associated with leaving), `cancel_rate` 0.052.
Logistic regression coefficients (standardised features): `frequency` −1.698 (more orders → less likely to lapse), `monetary` +0.285 (given the order count, higher spend slightly raises lapse risk; frequency and monetary are correlated, so this sign is a conditional effect and should not be read alone), `cancel_rate` −0.124 (weak and slightly negative, effectively little signal).

The selected pipeline is saved with `joblib.dump` to `outputs/lapse_model.joblib`; the reloaded model reproduces the test predictions and probabilities exactly (checked in code). `outputs/retention_list.csv` (columns `customer_id, lapse_probability, actually_lapsed`) holds the top 10 Premium-segment customers in the test set by predicted lapse probability (40 Premium customers are in the test set); **1 of the 10 truly lapsed**. The Premium flag comes from the whole-window RFM, which includes the September window that defines the lapse label, so this list is illustrative and not a leakage-free evaluation.

## Part C

Pipeline: `src/part_c_triage.py`. Tickets are processed in file order; `tickets.csv` is read with `keep_default_na=False`.

### Guardrails and redaction
4 empty tickets get `skipped_empty`, 4 long tickets (734 estimated tokens each, limit `MAX_INPUT_TOKENS = 400`) get `flagged_long`; neither is ever sent to the model. Redaction applies, in order, the email, phone and order-id patterns from the brief:

| Type | Substitutions |
|---|---|
| email → `[EMAIL]` | 55 |
| phone → `[PHONE]` | 91 |
| order id → `[ORDER_ID]` | 132 |
| **Total** | **278** |

Re-applying the three patterns to the redacted texts finds 0. The user message is exactly the redacted ticket text, and the code asserts for every call that it contains no email, phone or order id.

### Prompts
Zero-shot (33 estimated tokens) and few-shot (121 estimated tokens; contains a line `EXAMPLES:` followed by four labelled examples including a fraud one). Both contain `CLASSIFY`, list the four categories and require a JSON-only reply.

### Retries and validation
Each call is wrapped in a retry function: up to 3 retries, wait `0.05 × 2**n × uniform(0.9, 1.15)` seconds, one log line per retry (for example `RETRY ticket=T0002 retry=0 wait=0.0530s`). Every full run has exactly 19 `TransientLLMError`s, all recovered at retry number 0 with waits 0.0453–0.0562 s; no ticket ended with a permanent error. `mock_llm.reset()` is called immediately before each run.

Replies are parsed as JSON (valid category → `classified_json`); otherwise lowercase words are extracted with `re.findall(r"[a-z]+", ...)` and accepted only if exactly one category word is present (`classified_keyword`); everything else, including JSON with an unknown category such as `shipping`, becomes `flagged_invalid_output` and goes to human review. Never a guess.
Status counts for one full run over the 156 eligible tickets: **135 classified_json, 12 classified_keyword, 9 flagged_invalid_output** (the same for both prompts).

### Zero-shot versus few-shot

| Run | Classified | Accuracy | Total tokens | Tokens per classified ticket |
|---|---|---|---|---|
| Zero-shot | 147 | 85.7% (126/147) | 9,556 | 65.0 |
| Few-shot | 147 | 100.0% (147/147) | 23,284 | 158.4 |

Zero-shot confusion table (rows = true, columns = predicted):

| true \ predicted | billing | delivery | fraud | technical |
|---|---|---|---|---|
| billing | 38 | 0 | 0 | 0 |
| delivery | 0 | 36 | 0 | 0 |
| fraud | 11 | 0 | 23 | 0 |
| technical | 10 | 0 | 0 | 29 |

Every zero-shot error is a fraud ticket predicted as billing (11) or a technical ticket predicted as billing (10). The few-shot prompt costs about 93 extra tokens per classified ticket (158.4 versus 65.0, roughly 2.4× the tokens) and buys 14.3 percentage points of accuracy, removing all 21 errors. It is worth paying when a mistake is expensive: a fraud ticket sent to billing misses the 2-hour security deadline, and the extra cost is small in absolute terms. For low-stakes categories, or at very large volume with a budget cap, zero-shot is adequate.

## Part D

### Chunks and retrieval
40-word chunks with 10-word overlap: 15 chunks (refund 4, delivery 3, escalation 3, payment 3, privacy 2), source file kept with every chunk. TF-IDF (`TfidfVectorizer()` fitted on the chunks, cosine similarity) ranks chunks; for `refund policy late delivery` the top three all come from `refund_policy.txt`.

TF (term frequency) measures how often a word appears in a chunk, and IDF (inverse document frequency) down-weights words that appear in many chunks so rare, informative words count more. A limitation: TF-IDF matches words, not meaning, so a question and a policy sentence that say the same thing in different words (for example "money back" versus "refund") get a low score.

`answer(question)` retrieves three chunks and sends a `POLICY ASSISTANT` system message plus a user message `CONTEXT:\n[source]\ntext…\nQUESTION:\n…` to the mock.

### Evaluation (`data/raw/policy_eval.csv`)

| Setting | expected_doc in top 3 (of 12) | expected_fact in answer (of 12) | fallback on the 2 unanswerable |
|---|---|---|---|
| 40 words, overlap 10 (15 chunks) | 12 | 12 | 2 |
| 40 words, overlap 0 (13 chunks) | 12 | 10 | 2 |

With overlap 0 two questions break: "What delivery time makes a completed order eligible for a full refund?" (answer returned: "receives a full refund of the order amount.", because the phrase "more than 45 minutes" lies in the neighbouring chunk) and "How soon is money returned when a payment fails but is deducted?" (the sentence is cut after "returned automatically", so "48 hours" is in the next chunk). In both cases the answer sentence is split across a chunk boundary; overlap keeps one chunk with the full sentence.

### Tools and agent
`src/agent.py` defines five tools in `TOOLS_SPEC` (name, one-sentence description, parameter spec) and `TOOL_MAP`: `get_order` (reads `data/instamart.db`), `search_policy` (the same `retrieve` as above), `calculate_refund` (completed order delivered > 45 minutes → 100% of the amount, otherwise 0), `issue_refund` and `escalate_to_human` (each appends a timestamped line to `outputs/refund_ledger.jsonl`; refunds above INR 1000 are escalated, not issued). The ledger append is idempotent: the same tool is never recorded twice for the same order, which protects against a double payout when a crashed run is replayed.

`run_agent(user_message, scenario_id, max_iterations=6, token_limit=6000, time_limit_seconds=10)` runs the ReAct loop and returns `status, final_answer, steps, llm_calls, tokens_used`. Each run is appended to `outputs/agent_runs.jsonl` (exactly 7 lines); the demonstrations are in `outputs/agent_demo_runs.jsonl`.

| S3 | ESCALATE | 1999.00 | 5 | 979 |

### Crash and resume
After every tool observation a checkpoint `state/<run_id>.json` is written (run id, scenario id, full message list, tokens used, step number, tools executed, steps, model-call count). For S1 a `SimulatedCrash` was raised right after the second tool's checkpoint, then `resume_agent("S1-crashdemo")` continued. Tools executed across the crash and the resume, in order: **get_order, search_policy, calculate_refund, issue_refund**, four executions, none repeated. Final status REFUND, INR 128.25, 5 model calls in total. (The ledger already held S1's refund from the scenario run, so the idempotent ledger did not add a second payout line.)

### ReAct versus plan-and-execute
Measured with the ReAct agent: 5 model calls for a refund or escalation (S1–S3, about 980–990 tokens), 4 for an on-time order (S4), 3 for a cancelled order (S5) and 2 for a missing order (S6, 110 tokens). A plan-and-execute design asks the model once for the whole step list, so a refund would take about 2 model calls (plan plus final answer) and far fewer tokens, since the growing message history is not resent on every step. The cost is rigidity: the plan is written before the first observation. With NOT_FOUND or a cancelled order, the fixed plan would still try the remaining steps, or must detect the error and replan, which is an extra model call and more code. ReAct reads each observation and stops at the right moment (2 calls for a missing order). For this refund workflow I would choose ReAct: it handles unexpected observations naturally and money is at stake, so a decision per step with checkpoints and limits is safer; the token difference is small at about 1,000 tokens per request. If volume made cost dominant, I would use plan-and-execute for the common happy path with replanning on any error.

## Limitations and Next Steps

- **Retention list is illustrative.** The Premium flag is a post-hoc whole-window label computed from RFM that includes the September window which defines the lapse label, so `outputs/retention_list.csv` is illustrative and not a leakage-free evaluation (the model's own features use only orders before 2025-09-01). Only 1 of its 10 customers truly lapsed, so Premium customers in this synthetic data rarely lapse.
- **One split, small data.** Test F1 comes from a single 232-row split (89 lapsed); differences of a few points between logistic regression and the forest are within noise. Next: repeated cross-validation and calibrated probabilities.
- **Over-sampling by duplication** raises recall at the cost of precision; threshold tuning on a validation set would be a cleaner way to trade them off.
- **Median imputation** of delivery times and ages (by category and city) removes information and understates variance; the 774 imputed delivery times and 67 ages are a small share but affect averages.
- **Mock model.** Part C accuracy (85.7% / 100%) and Part D answers come from a keyword-based mock, so they show the pipeline's guardrails, not real language-model quality. Next: swap in a hosted model behind the same interface and re-measure.
- **TF-IDF retrieval** matches words, not meaning; an embedding retriever would handle paraphrases. Chunk size and overlap were fixed by the brief.
- **Refund agent** assumes every request is inside the 7-day window and does not verify that the customer owns the order; a production version should check both, and escalated refunds need a real approval workflow.
- **Data is synthetic**; none of the numbers describe a real business.
